# Engineering Workflow

This document is the single source of truth for how work is done in this repository. The agent
must follow it (see `AGENTS.md`), and humans are expected to as well.

## Principles

- **One decision, one ADR.** Any non-trivial decision is recorded before or alongside its
  implementation.
- **All work is planned.** Nothing is implemented outside a plan; plans decompose into tickets.
- **Tickets are atomic.** One deliverable each, independently verifiable, committed alone.
- **Every ticket ends in a commit.** Never commit red; `task check` must be green first.
- **Every session leaves a diary entry.** Chronological memory of the project.
- **Excellent tooling.** Code stays clean, formatted, linted and tested.

## Artifacts

| Artifact | Location                              | Template                 | Nature                        |
|----------|---------------------------------------|--------------------------|-------------------------------|
| ADR      | `docs/adr/NNNN-<slug>.md`             | `docs/templates/adr.md`  | Immutable once accepted       |
| Plan     | `docs/plans/<plan-name>/README.MD`    | `docs/templates/plan.md` | Living until the plan closes  |
| Ticket   | `docs/plans/<plan-name>/ticket-NNN.md`| `docs/templates/ticket.md`| Atomic, status-tracked       |
| Finding  | `docs/plans/<plan>/findings/<id>.md`  | `docs/templates/finding.md`| Output of a spike            |
| Diary    | `docs/diary/entry-YYYY-MM-DD-<slug>.md`| `docs/templates/diary.md`| Append-only, one per session  |

## ADRs (Architecture Decision Records)

- Every non-trivial decision produces an ADR.
- Format: MADR-lite — **Context**, **Decision**, **Consequences**, **Alternatives considered**.
- Globally numbered, zero-padded to four digits (`0001`).
- **Accepted ADRs are immutable.** To change a decision, write a new ADR and set
  `supersedes` / `superseded_by` on both.
- Status lifecycle: `proposed` → `accepted` → (`superseded` | `deprecated`).
- Avoid naming volatile tools or versions inside an ADR's **Decision**; they go stale (this is how
  the Make→Task rename left stale references). Refer to the capability, and mention specific tools
  in **Consequences** if needed.
- Browse the index at `docs/adr/README.md` (generated by `task adr:index`).
- Create one with `task new-adr title="..."`.

## Plans

- A plan is a bounded body of work with a goal and a plan-level Definition of Done.
- Lives at `docs/plans/<plan-name>/README.MD`; the plan name is kebab-case.
- Has a `kind`: `product` for feature work, `meta` for tooling, workflow and documentation. Meta
  work is the **only** exception to "no implementation outside a product plan".
- Contains a **ticket index table** that is **generated** from ticket frontmatter — never edit it by
  hand; run `task plan:sync`.
- A plan is `draft` until reviewed, then `active`, then `done`.
- Create one with `task new-plan name=... title="..."`.

## Tickets

- **Atomic:** a single deliverable that can be reviewed and verified on its own.
- Frontmatter carries all metadata. Required fields:
  `id, title, plan, status, type, priority, estimate, depends_on, related_adr, created, updated, tags`.
- Body sections: **Context**, **Scope**, **Out of scope**, **Definition of Done** (checklist),
  **Quality Gates** (checklist), **Notes**.
- Status lifecycle: `todo` → `in_progress` → `review` → `done` (or `blocked` / `cancelled`).
- A ticket is **not started until its `depends_on` tickets are `done`**.
- **Spike output rule:** a `spike` ticket may only reach `done` if it produced a decision — a linked
  ADR in `related_adr`, or a finding at `docs/plans/<plan>/findings/<id>.md` declared in the
  `finding` field.
- Start and close with `task ticket:start id=... [plan=...]` and `task ticket:close id=...`; start
  refuses if a dependency is not `done`, and close updates the plan index for you.
- Create one with `task new-ticket plan=<plan-name> title="..."`.

## Commits

- **Trunk-based.** Work lands on `main`. Short-lived branches are allowed but never long-lived.
- **Exactly one commit per ticket**, using Conventional Commits and referencing the ticket id:

  ```
  feat(games): add azerothcore adapter (ticket-010)
  ```

- The commit contains: the code, its tests, the ticket file (status set to `done`), the plan index
  update, any ADR the ticket produced, and the diary entry if it is the session's last ticket.
- Commit only when the ticket's Definition of Done and Quality Gates are checked.
- Enforce the format with the `commit-msg` hook: install it once with `task hooks:install`, and use
  `task verify:commits range=origin/main..HEAD` in CI. Merge/revert commits are exempt; use an
  explicit `[no-ticket]` for other genuine exceptions.
- `task changelog` regenerates `CHANGELOG.md` from history with git-cliff.

## Diary

- One entry per work session: `docs/diary/entry-YYYY-MM-DD-<session-slug>.md`.
- Records **Intent**, **What happened**, **Decisions / ADRs**, **Blockers**, **Next**.
- Append-only: never rewrite a past entry.
- Create one with `task new-diary slug=...`; commit it with the session's final ticket commit.

## Releases and versioning

- One **unified CalVer** version for the whole monorepo: `vYYYY.MM.PATCH`. `PATCH` increments within
  a month and resets to `0` on a new month (ADR-0018).
- Releases are ad-hoc and **do not map to plans**; `meta` plans never release.
- Git tags are the source of truth; `task build` injects the version via ldflags and the app exposes
  it through an endpoint.
- The HTTP API is versioned independently at `/api/v1`; a breaking change creates a new path version.
- There is no product-level compatibility promise yet — the API path version is the boundary.
- `task release` computes the next version, requires a clean tree and green gates, tags, regenerates
  the changelog and pushes the tag when a remote exists. `task release:dryrun` previews;
  `task version` / `task version:next` print the current and next versions.

## Quality gates

`task check` runs `fmt` + `vet` + `lint` + `test` (with `-race` where cgo is available; CI runs it)
and the workflow tool's tests. `task check:ci` adds `task verify`, the path-filtered `console` gate
and `govulncheck`. `task coverage` enforces a coverage floor (`COVERAGE_MIN`, default 60). Every
ticket's Definition of Done must include: tests added/updated, docs updated, and the gates green.

## Tooling

Go 1.27+, `golangci-lint` v2, [Task](https://taskfile.dev) (go-task), Node 26+, bash.

```
task               # list tasks
task check         # fmt + vet + lint + test (-race)
task check:ci      # check + verify + console + govulncheck
task coverage      # tests with coverage floor (COVERAGE_MIN)
task console       # lint/typecheck the console (path-filtered)
task fmt vet lint test build run tidy
task verify        # validate workflow artifacts
task plan:sync     # regenerate plan indexes
task adr:index     # regenerate the ADR index
task ticket:start  id=... [plan=...]
task ticket:close  id=... [plan=...]
task hooks:install # install the commit-msg hook
task verify:commits range=origin/main..HEAD
task changelog     # regenerate CHANGELOG.md (needs git-cliff)
task version       # current version from git tags
task version:next  # next CalVer
task release       # cut a release
task release:dryrun
task new-adr       title="..."
task new-plan      name=... title="..."
task new-ticket    plan=... title="..."
task new-diary     slug=...
```

CI mirrors `task check` and `task verify`.
